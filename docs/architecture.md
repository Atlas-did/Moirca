# 架构设计（云端版）

> 目标：把 MiroFish 的“多 Agent 并行调研 → 融合计算 → 报告生成”pipeline，落到高考志愿填报场景。
> 本文只描述 MVP（P0-P2）必须的系统边界与数据流。

## 1. 系统边界

### 1.1 组成
- 前端：表单 + 3 步决策树问答 + 结果/对比/报告页
- 后端：FastAPI 提供 API；负责数据检索、Agent 调用、融合与报告生成
- 数据层：公开数据、独家数据、语料库、用户查询记录（最小化）

### 1.2 关键原则
- 解释优先：任何推荐都必须可解释、可引用
- 可降级：爬虫失效/LLM 不可用时仍能返回“基础规则推荐 + 明确提示”
- 可追溯：每次输出能定位到使用的数据版本、语料引用、规则版本

---

## 2. 端到端数据流

1) 用户输入
- `score` / `province` / `exam_type`
- 决策树 3 步选择（step1/2/3）

2) 候选池生成（P1 具备）
- 规则过滤（分数段/科类/排除项）
- 数据检索（公开数据、独家数据、语料库）

3) Agent 并行调研（P2 逐步补齐）
- Agent 1 官方猎手：公开数据可信源
- Agent 3 时效警犬：专业/政策时效标记
- Agent 4 矛盾侦探：冲突识别与降级策略
- Agent 5 趋势先知：就业倒推 + 张雪峰框架修正（以“解释”为主）

4) Agent 6 融合炼金术士
- 计算 `match_score`
- 生成 breakdown（每个 Agent 的贡献、时效衰减、置信度）
- 输出 TopN + 冲稳保分层

5) Agent 7 报告生成器
- Markdown 报告：推荐 + 冲稳保 + 风险 + 对比结论 + 引用

---

## 3. 运行形态

### 3.1 同步接口 vs 异步任务
- P0/P1：同步（接口直接返回）
- P2：报告生成建议异步（接口返回 `job_id`，前端轮询或 SSE）

### 3.2 生产部署建议
- FastAPI（Uvicorn/Gunicorn）
- SQLite（允许云端先上线验证；后续可迁移 PostgreSQL）
- 对象存储（可选）：用户上传的“录取截图”（如启用社区飞轮）；PDF 导出放到 P3
- 日志：结构化日志（JSON），敏感字段脱敏

---

## 4. 关键数据分层

### 4.1 公开数据（Public）
- 分数线 / 位次表 / 招生计划 / 院校专业目录

### 4.2 独家数据（Private moat）
- 朋友网络结构化数据（转专业难度、隐形门槛、真实毕业去向…）
- 必须：结构化入库 + 标注提供者 + 可验证状态

### 4.3 语料库（Wisdom）
- 张雪峰语录/框架：用于“解释”和“趋势修正”

---

## 5. 可解释性输出规范（强约束）

推荐条目至少包含：
- `reason`：一句话理由（面向用户）
- `evidence`：2-5 条证据点（数据字段/语料引用/规则命中）
- `risk_note`：风险提示（如果有）
- `confidence`：置信度（0-1 或 0-100）

低置信度降级策略：
- 不给 Top1 “强烈推荐”，改为“备选/需核验”
- 强制展示“需要你确认的关键变量”（如是否服从调剂）
